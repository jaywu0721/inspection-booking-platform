# 驗屋預約管理系統｜現行功能與邏輯完整說明

> **文件目的**：把目前已上線的功能、權限、資料關聯、預約規則與限制一次說清楚，作為管理、交接與後續改版的基準。本文描述的是目前程式碼狀態，不是未來規劃。
>
> **程式版本基準**：`3bb0385e`（後台代客預約與編輯改期均支援客製日期／自訂時段）  
> **盤點日期**：2026-10-09  
> **正式網域**：`https://inspect.eaglebuilt.company`、`https://inspectionshop-chxaqqnk.manus.space`

## 1. 系統定位與核心原則

此系統是給**多家建設公司、多個建案**共用的驗屋預約平台。它把原本容易分散在 Excel、LINE、電話或人工表單的資料，收斂成以下一條資料鏈：

```text
公司
└─ 建案
   ├─ 住戶聯絡資料（同一戶可有多支手機）
   └─ 預約連結（初驗／複驗、各自開放期間）
      ├─ 公開時段（可供住戶選擇、具名額）
      └─ 預約紀錄
         └─ 改期歷程
```

### 1.1 最重要的設計決策：**預約連結是作業單位**

系統不是用「建案」直接開放預約，而是由建案建立一筆或多筆**預約連結**。每一筆連結都有自己獨立的：

- 初驗／複驗類型；
- 分享 Token 與專屬網址；
- 啟用／停止狀態；
- 開放起訖時間；
- 可選時段；
- 已完成預約與未完成住戶判定。

因此，同一建案可以同時有不同梯次、不同用途或不同階段的連結；**時段不會在連結間共用**。這是避免舊梯次時段誤帶到新梯次的基礎規則。

## 2. 角色、入口與權限邊界

| 角色／入口 | 如何進入 | 可以做什麼 | 不能做什麼 |
| --- | --- | --- | --- |
| 一般訪客 | 根網址未帶預約參數 | 看到管理員登入頁 | 不會看到通用住戶預約首頁或示範資料 |
| 住戶 | 公司提供的專屬分享網址 | 查看該建案品牌內容、驗證身分、查詢既有預約、新增預約或在開放期間自行改期 | 無法看後台、無法建立／編輯一般時段、無法使用客製時段 |
| 管理員 | 根網址或 `/admin`，再登入 | 管理公司、建案、住戶、連結、時段、預約、代客預約、改期與匯出 | 目前沒有後台帳號管理、權限分級或稽核報表畫面 |

### 2.1 網址分流

| 網址型態 | 實際畫面 | 說明 |
| --- | --- | --- |
| `https://網域/` | 管理員登入 | 根網址刻意不作為住戶入口，避免客戶與管理入口混用。 |
| `https://網域/admin` | 管理員登入／後台 | 與根網址同一套後台。 |
| `https://網域/?link=分享Token` | 住戶預約頁 | **正式建議使用方式**。Token 對應單一預約連結。 |
| `https://網域/?company=...&project=...&type=initial` | 住戶預約頁 | 相容舊格式；若同一建案同類型有多筆連結，系統會拒絕並要求使用完整 Token 網址。 |

### 2.2 管理員登入機制

- 帳密存在 `adminCredentials` 資料表；密碼採 **scrypt + 隨機 salt** 雜湊儲存，不保存明碼。
- 登入成功後會取得 HMAC 簽章的 Session Cookie：`HttpOnly`、`Secure`、`SameSite=Lax`。
- Session 有效時間為 **12 小時**。
- 後台新增、修改、刪除、改期、代客預約與可用名額查詢都要求有效管理員 Session。
- 未登入者查詢 Dashboard 與預約清單時只會拿到空資料；真正的寫入操作會被後端拒絕。

> 目前資料表可容納多筆管理員帳號，但後台尚未提供建立、停用、改密碼、角色分級或操作紀錄的管理介面；實務上目前是單一管理員作業模式。

## 3. 資料模型與每張資料的用途

| 資料表／概念 | 主要欄位與用途 | 現行規則 |
| --- | --- | --- |
| `companies` 公司 | 名稱、Logo、電話、首頁主標題、流程、注意事項、FAQ、聯絡窗口 | 公司層級內容會顯示到該公司所有建案的住戶前台。 |
| `projects` 建案 | 所屬公司、名稱、地址、戶號格式提示、戶號範例 | 建案只保存差異資訊；目前沒有建案層級覆寫 FAQ／流程文案的功能。 |
| `residents` 住戶 | 公司、建案、戶號、手機、備註 | 同建案內同一「戶號＋手機」不可重複；同戶可用不同手機建立多筆聯絡人。 |
| `bookingLinks` 預約連結 | 公司、建案、初驗／複驗、Token、開放時間、啟用狀態 | 一筆連結是一個獨立預約作業單位。 |
| `bookingSlots` 時段 | 日期、起訖文字、名額、啟用狀態、所屬連結 | 分為公開時段與管理員私有客製時段。 |
| `bookings` 預約 | 住戶、連結、時段、戶號／手機快照、Email、驗屋公司、狀態、內部備註 | 戶號與手機會存快照，保留當時預約資料。 |
| `bookingReschedules` 改期歷程 | 原時段、新時段、備註、時間、操作者 | 每次改期皆追加一筆歷程；不覆寫舊時段。 |
| `adminCredentials` | 管理員帳密雜湊與啟用狀態 | 供獨立後台登入使用。 |

### 3.1 公開時段與私有客製時段

| 類型 | 建立方式 | 名額 | 前台可見 | 一般時段管理可見 | 用途 |
| --- | --- | ---:| --- | --- | --- |
| **公開時段** | 管理員手動建立或快速批次建立 | 管理員設定，至少 1 | 是，但住戶只看明天以後且有餘額者 | 是 | 正常住戶預約與一般改期。 |
| **私有客製時段** | 管理員改期／代客預約時輸入客製日期與自訂時段 | 固定 1 | 否 | 否 | 僅供建立它的那一筆預約使用。 |

私有時段會標記為 `isPrivate=true`，並附上一組隨機 `uniquenessScope`。即使同一連結、同一天、同一時間已存在另一筆私有例外預約，仍可各自建立，不會撞到公開時段的唯一性限制。

## 4. 住戶前台功能與完整流程

### 4.1 前台載入的內容

住戶透過有效分享連結進入後，可看到：

1. 公司 Logo、公司名稱、建案名稱、聯絡電話；
2. 公司主標題與主視覺說明；
3. 驗屋流程、交屋流程、注意事項、FAQ、聯絡窗口；
4. 「詳細交屋流程圖」；
5. 該連結的開放起訖時間與狀態：**開放中／即將截止／已截止**；
6. 戶號與手機驗證欄位。

連結被判定為不可操作的條件如下，前台統一視為「已截止」或未開放：

```text
手動停止 isEnabled = false
或 現在時間早於 startsAt
或 現在時間晚於 endsAt
```

### 4.2 住戶身分驗證

住戶必須同時輸入：

- 標準戶號；
- 該戶**任一支已登錄手機號碼**。

後端會以「目前分享連結所屬建案＋戶號＋手機」精確比對。驗證成功後才會顯示該戶資料、既有預約與可操作的預約區。

- 同一戶有兩位或以上聯絡人時，只要輸入其中一支已登記手機即可驗證。
- 驗證失敗不會透露住戶是否存在，只提示確認戶號格式與手機或聯絡窗口。
- 行動裝置驗證成功後，畫面會自動捲動到「選擇新的預約時段」區域，避免停在既有紀錄上方。

### 4.3 既有預約顯示

驗證成功後，住戶會看到該建案、該戶所有未取消的既有預約紀錄，包含初驗／複驗、狀態、日期與時段。

但要注意兩個層次：

- **畫面顯示**：可看到同建案、同戶的既有預約。
- **前台自行改期**：只允許操作「目前這一筆分享連結」下的預約；不能用 A 連結去改 B 連結的預約。

### 4.4 新增預約流程

```text
分享連結進站
→ 輸入戶號＋已登記手機驗證
→ 選日期
→ 選該日可用時間
→ 選填 Email、勾選是否有驗屋公司
→ 送出
→ 後端鎖定時段並再次檢查名額
→ 成功後重新載入既有預約
```

#### 住戶看得到哪些時段？

前台只會回傳同時符合以下條件的**公開時段**：

1. 屬於目前預約連結；
2. 時段已啟用；
3. `isPrivate=false`；
4. 預約連結仍在開放期間；
5. 依 **Asia/Taipei** 日期判斷為**明天或更晚**；
6. 尚有剩餘名額。

所以住戶無法預約：

- 當日；
- 已過日期；
- 已額滿時段；
- 停用時段；
- 私有客製時段；
- 已截止或尚未開放的連結。

#### 新增預約的資料驗證與保護

- Email 為**選填**；若有填寫，必須符合一般 Email 格式，不限 Gmail。
- 「是否有驗屋公司」為布林欄位，可勾選。
- 同一戶號在**同一預約連結**下，只能有一筆未取消的成功預約。
- 系統以戶號快照判斷重複，而不是只看某一筆住戶 ID；因此同戶多支手機也不能在同一連結重複預約。
- 最後一個名額採資料庫交易與列鎖再次檢查，先送出且成功鎖定者取得名額；較晚送出者會收到額滿訊息。
- 同一戶仍可在不同預約連結下預約，例如不同梯次或初驗／複驗連結，因為防重規則是以 `linkId` 為範圍。

### 4.5 住戶自行改期

前台只在「此戶已於目前連結完成預約」時顯示「修改日期」。

#### 住戶可改的內容

- 新日期與公開時段；
- 此次是否由驗屋公司陪同。

#### 住戶不能改的內容

- Email；
- 後台內部備註；
- 客製日期；
- 自訂時段；
- 已截止連結下的日期／時段。

#### 改期防呆與資料一致性

- 連結必須仍在開放期間。
- 不可選擇目前同一個時段。
- 目標時段必須是同一連結下啟用、公開、明天以後且尚有名額的時段。
- 每次選日期、展開／操作時段區以及送出後，介面都會重新同步可用名額。
- 後端會檢查送出時的 `currentSlotId` 是否仍是原時段；若其他操作已先更新該預約，會提示「預約資料已更新，請重新整理後再試」。
- 成功後，`bookings.status` 變為 `rescheduled`，並新增一筆改期歷程，`changedBy=customer`。

#### 連結截止後的行為

住戶仍可驗證並查看既有預約；但不能新增預約，也不能自行改期。此時需由管理員後台協助。

## 5. 後台功能：公司、建案與住戶

### 5.1 公司管理

後台可新增與編輯：

- 公司代號（slug；建立後在畫面上不可改）；
- 公司名稱、Logo URL、聯絡電話；
- 前台主標題與主視覺說明；
- 驗屋流程、交屋流程、注意事項；
- FAQ（每行「問題 | 回答」）；
- 聯絡窗口說明。

這些內容是**公司層級共用內容**。同公司任何建案的住戶預約頁都會使用它。

> 目前前台可顯示公司 Email（資料表也保留欄位），但現行公司管理畫面沒有編輯 Email 的欄位。若需變更該值，必須補功能或經由受控資料維護處理。

### 5.2 建案管理

後台可新增建案，設定：

- 所屬公司；
- 建案名稱；
- 地址；
- 戶號格式提示；
- 戶號範例。

建案 slug 由系統依建案名稱與公司 ID 產生。**目前介面有新增與刪除，沒有既有建案的編輯按鈕**；雖然資料層支援更新，但尚未接成畫面操作。

### 5.3 住戶資料管理

後台可逐筆建立住戶資料：公司 → 建案 → 戶號 → 手機 → 備註。

- 公司與建案必須正確對應，不能把 A 公司的建案掛到 B 公司。
- 同一建案可用相同戶號建立多筆不同手機，支援多位聯絡人。
- 住戶清單可依建案篩選。
- 現行畫面提供新增、篩選、刪除；沒有編輯既有住戶資料的按鈕。

## 6. 後台功能：預約連結與時段管理

### 6.1 預約連結管理

建立或編輯連結時，可設定：

- 公司、建案；
- 類型：`initial`（初驗）或 `reinspect`（複驗）；
- 啟用開始時間、結束時間；
- 是否啟用。

建立成功時系統產生不可重複的分享 Token，後台可：

- 複製完整分享網址；
- 另開分頁測試住戶頁；
- 編輯連結設定；
- **停止**連結；
- 重新啟用連結；
- 刪除連結。

「停止」和「刪除」意義不同：

| 操作 | 對住戶前台 | 資料是否保留 |
| --- | --- | --- |
| 停止連結 | 立即不可新增／自行改期；仍可驗證查看既有預約 | 保留連結、時段、預約及歷程 |
| 刪除連結 | 分享網址失效 | 連同此連結的時段、預約與改期歷程真刪除 |

### 6.2 一般時段管理

公開時段必須明確掛在一筆預約連結下。可設定：

- 單一日期；
- 起始／結束時間文字；
- 名額（至少 1）；
- 啟用或停用。

#### 建立方式

1. **單筆建立／編輯**：選日期、填起訖時間與名額。
2. **快速建立常用時段**：預設為：
   - 09:00–10:30
   - 10:30–12:00
   - 14:00–15:30
   - 15:30–17:00
3. **日期區間批次建立**：把目前填寫的常用時段套用到區間中每一天。

#### 快速建立的規則

- 預設時段可以在當次送出前修改；不影響下次預設值。
- 不必四筆都填。完全空白的列會跳過。
- 至少要有一筆完整起訖時間。
- 只填開始或只填結束，系統要求補齊或清空。
- 同一批次內重複的起訖組合會被拒絕。
- 同一連結、同一日期、同一時間的公開時段不能重複建立；前端與後端都會檢查。
- 日期區間開始日不可晚於結束日。

#### 時段名額與刪除規則

- 剩餘名額 = `時段設定名額 - 綁定此時段且狀態不是 cancelled 的預約數`，最低顯示為 0。
- 已額滿時段不能被住戶與管理員的一般時段流程選取。
- 時段已有任何預約紀錄時，為保留歷程，不能直接刪除。
- 一般時段清單不會顯示私有客製時段。

## 7. 後台功能：預約紀錄、匯出、改期與代客預約

### 7.1 預約紀錄查詢與篩選

後台可用以下條件組合查詢：

- 建案；
- 該建案的預約連結；
- 戶號（模糊查詢）；
- 類型（初驗／複驗）；
- 狀態（`booked`、`rescheduled`、`cancelled`）；
- 預約日期。

結果依時段日期、開始時間、結束時間、預約 ID 排序，並顯示：公司／建案、戶號、類型、日期時段、是否有驗屋公司與目前狀態。

### 7.2 Excel 匯出

「下載預約清單」只匯出**目前篩選結果**，不會無差別下載全部預約。

匯出規則：

- 檔名：`驗屋預約清單.xlsx`；
- 工作表：`驗屋預約`；
- 依日期分組，格式為 `M/D(星期)`；
- 同日依開始時間、結束時間、戶號排序；
- 每個預約格顯示：`戶號(開始-結束)`；
- 勾選「有驗屋公司」的預約格以**黃色**底色標記。

### 7.3 後台編輯改期

在預約紀錄列按「編輯改期」後，可修改：

- 新日期；
- 新時段；
- 內部備註；
- 此次是否有驗屋公司。

管理員改期與住戶改期不同之處：

| 規則 | 住戶前台 | 管理員後台 |
| --- | --- | --- |
| 連結截止後可否操作 | 不可 | 可以 |
| 一般既有時段可否選今天／過去日期 | 不可 | 可以，依該連結已建立的時段為準 |
| 客製日期 | 不可 | 可選今天與未來，不能選過去 |
| 自訂時段 | 不可 | 可用單一欄位輸入 `HH:mm-HH:mm` |
| 可否改驗屋公司勾選 | 可以 | 可以 |

一般改期時，後台會在：

1. 選日期後；
2. 展開時段下拉時；
3. 最終送出交易內；

同步並再次檢查最新餘額，避免畫面看到的名額與實際寫入不一致。

成功時：

- 原時段不被覆寫刪除；
- 新增一筆 `bookingReschedules` 改期歷程；
- `changedBy` 記錄為登入管理員帳號；
- 預約狀態改為 `rescheduled`；
- 目前內部備註與是否有驗屋公司更新到預約主檔。

### 7.4 客製日期與自訂時段（僅管理員）

後台「編輯改期」與「代客預約」都提供相同能力：

```text
選既有日期／時段
或
選「客製日期」→ 選今天或未來日期 → 選「自訂時段」→ 輸入 HH:mm-HH:mm
```

#### 驗證規則

- 客製日期格式必須是合法 `YYYY-MM-DD`。
- 日期不可早於 Asia/Taipei 的今天。
- 時段格式必須是 `HH:mm-HH:mm`，例如 `14:00-16:00`。
- 小時為 00–23、分鐘為 00–59。
- 結束時間必須晚於開始時間。
- 既有時段 ID 與 `customSlot` 只能二選一，不能同時傳，也不能兩者皆未選。

#### 自訂時段寫入結果

系統不會把自訂時段混進一般時段，而是建立一筆：

```text
capacity = 1
isActive = true
isPrivate = true
uniquenessScope = 每筆隨機值
```

此時段只由該筆預約的 `slotId` 指向，並且：

- 不會出現在住戶前台時段清單；
- 不會列在後台一般時段管理；
- 不會進入一般可用名額計算；
- 不可被另一筆一般預約或一般改期重複使用；
- 仍可在預約紀錄及改期歷程中保留正確日期／時間。

### 7.5 未完成預約住戶與代客預約

管理員必須先選擇「建案」及「該建案對應預約連結」，才能查看未完成住戶。

未完成判定規則：

1. 只看目前所選建案與所選連結；
2. 同一戶號會先標準化（去空白、轉大寫）後去重；
3. 該戶若在此連結下有任何**未取消**預約，就不會列入；
4. 若只有 `cancelled` 預約，則仍視為未完成，可再安排；
5. 同戶有多支手機時，清單只顯示一筆代表資料，避免重複列戶。

點「代客預約」後，管理員可填：

- 既有公開日期／時段，或客製日期＋自訂時段；
- Email（選填）；
- 內部備註；
- 是否有驗屋公司。

代客預約成功後：

- 寫入一筆正式預約；
- 備註寫入預約主檔；
- 該戶立即自未完成清單移除；
- 即使連結已截止，後台仍可以代客建立預約；
- 仍保留住戶所屬建案、連結歸屬與同連結重複預約阻擋。

## 8. 一致性、名額與競態保護

### 8.1 交易層保護

所有關鍵預約／改期在資料庫交易內再次判斷，不能只相信畫面：

| 情境 | 後端保護 |
| --- | --- |
| 新預約搶最後名額 | 鎖定時段資料列，重算未取消預約數，滿額即拒絕。 |
| 改期搶最後名額 | 鎖定原預約與新時段，重算名額，滿額即拒絕。 |
| 改期資料過期 | 比對送出時的原時段 ID；不一致代表有人先改過，拒絕並提示重新整理。 |
| 跨連結／跨建案使用時段 | 重新檢查住戶、連結、建案與時段歸屬。 |
| 私有時段被當公開時段使用 | 一般預約、一般改期與可用時段查詢都明確排除 `isPrivate=true`。 |
| 同戶重複預約 | 同連結＋同戶號快照＋未取消預約存在時拒絕。 |

### 8.2 日期與時區

系統統一以 **Asia/Taipei** 解析、比對與顯示日期。

- 單純日期字串會轉為 UTC 正午保存，避免瀏覽器時區把日期推到前一天或後一天。
- 前台可選日期、後台日期篩選、時段建立、Excel 匯出和表格顯示都使用相同的台北日期鍵值。
- 「今天／明天／過去日期」規則以台北日期為準，不受使用者裝置時區影響。

## 9. 刪除規則與不可逆範圍

所有刪除操作在前端都要經過**兩次確認**。第二次確認後是實際真刪除，系統本身沒有復原按鈕。

| 刪除目標 | 現行結果 |
| --- | --- |
| 公司 | 刪除該公司下所有建案、住戶、連結、時段、預約與改期歷程。 |
| 建案 | 刪除該建案下所有住戶、連結、時段、預約與改期歷程。 |
| 預約連結 | 刪除該連結下時段、預約與改期歷程。 |
| 住戶 | 若任何預約紀錄引用此住戶，禁止刪除，以保留歷程；否則可刪。 |
| 公開時段 | 若任何預約紀錄引用此時段，禁止刪除；否則可刪。 |
| 私有客製時段 | 不列入一般時段管理，通常隨連結／建案／公司刪除而一起清除。 |

> **這樣做的風險是資料刪除不可逆。建議改成：正式作業優先用「停止連結」或「停用時段」，只有確認資料與歷程都不需要時才做刪除。**

## 10. 現行限制與操作風險

以下不是待辦承諾，而是目前版本的真實邊界，管理時不能忽略。

| 項目 | 現行狀態 | 風險／影響 |
| --- | --- | --- |
| 管理員帳號管理 | 沒有畫面可建立帳號、改密碼、停用帳號或做角色分級 | 帳密異動需由受控維運處理；不適合多人分權作業。 |
| 建案與住戶編輯 | 現行 UI 可新增、篩選、刪除，但沒有既有資料的編輯按鈕 | 建案名稱、地址、戶號或住戶手機錯誤時，沒有一般管理介面可直接修正。 |
| 取消預約操作 | 資料模型與篩選支援 `cancelled`，但沒有住戶端或後台端的取消按鈕 | 目前不能在一般操作畫面把預約改為取消。 |
| 手動一般時段格式 | 只要求起訖時間不可空白，未像客製時段一樣驗證 `HH:mm` 格式或結束晚於開始 | 可能建立排序或文字格式不一致的公開時段；輸入時需人工覆核。 |
| 預約連結起訖時間 | 表單要求兩者皆填，但目前未額外阻擋開始時間晚於或等於結束時間 | 建立／修改連結時需人工確認起訖順序。 |
| 建案內容繼承 | 流程、FAQ、注意事項為公司層級共用 | 修改公司文案會影響該公司所有建案；目前無建案個別覆寫。 |
| 通知整合 | 無 Email、簡訊、LINE、自動行事曆通知流程 | 預約成功、改期或截止不會自動通知住戶。 |
| 資料備份／回復 | Checkpoint 保護程式碼版本，不等於資料庫備份 | 人工直接誤刪資料庫內容無法靠程式版本自動恢復。 |

## 11. 管理員建議操作順序

### 新建案第一次啟用

```text
1. 建立或確認公司資料與前台文案
2. 建立建案（戶號格式提示與範例要先確認）
3. 匯入／逐筆建立住戶與手機
4. 建立初驗或複驗預約連結，設定開放起訖
5. 為「該連結」建立公開時段與名額
6. 後台複製分享網址，以無痕視窗檢查
7. 再把完整 ?link=... 網址發給住戶
```

### 日常例外處理

| 情境 | 建議使用功能 |
| --- | --- |
| 住戶未預約且不會操作 | 選建案＋連結 → 未完成預約住戶 → 代客預約。 |
| 已預約住戶要換一般時段 | 預約紀錄 → 編輯改期 → 選新日期與一般時段。 |
| 已預約住戶必須安排在非公開時段 | 編輯改期 → 客製日期／自訂時段；不可要求住戶自行操作。 |
| 連結已截止但需補登 | 管理員代客預約或後台編輯改期；住戶端不可操作。 |
| 暫時不想讓住戶繼續操作但要留紀錄 | 停止預約連結，不要直接刪除。 |
| 時段已經有預約但想不再提供給新人 | 將時段設為停用，不要嘗試刪除。 |

## 14. 一句話總結

目前系統的運作核心是：**每個建案可建立多筆彼此隔離的預約連結；住戶只在開放期間內，以戶號加已登記手機預約明天以後的公開時段；管理員可跨截止處理一般或私有客製時段，且所有名額、歸屬、重複預約與改期歷程都由後端交易規則再次把關。**
